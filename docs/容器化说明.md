# 容器化说明

本文说明如何把这个平台装进容器，以及**为什么某些写法必须改**才能装。

---

## 一、已经为容器化处理掉的问题

这些不是「理论上可能有问题」，而是改造前实际存在、会真出故障的点：

| 问题 | 后果 | 处理 |
|---|---|---|
| `PROJECT_ROOT` 从 `__file__` 推导 | `pip install` 后 `data/`、`models/`、`var/logs/` 全部落到 `site-packages` 附近 | 新增 `WQ_ROOT` 显式指定项目根；检测到已安装进 `site-packages` 时给出告警 |
| 调度器在 **import 期**启动 | `gunicorn -w 4` → 4 个调度器同时爬同一份数据，重复写库 | 新增 `WQ_ENABLE_SCHEDULER`，多 worker 部署可整体关闭 |
| `datetime.now()` 无时区 | 容器默认 UTC，`cron 2:00` 变成北京时间 10:00，数据日期归属整体错位 | `config.now()` + APScheduler 显式 `timezone=`，默认 `Asia/Shanghai` |
| 日志时间戳与业务时区不一致 | 日志打 UTC、业务算 +8，看日志会把 21:00 的事读成 13:00 | Dockerfile 同时设 `TZ`，`config` 里 `WQ_TZ` 优先、其次跟随 `TZ` |
| `torch.load(weights_only=False)` | pickle 反序列化 → 替换 `.pth` 即可执行任意代码 | 权重与缩放器分文件，权重走 `weights_only=True` |
| 日志目录不可写就崩 | 挂只读卷 / 权限不足时服务起不来 | 退化到仅控制台输出 |
| SQLite 默认 journal 模式 | 后台写库时接口报 `database is locked` | 开启 WAL |
| sklearn 是运行时依赖 | 镜像变大 + 跨版本 `InconsistentVersionWarning` | 缩放器改 JSON、算术用 numpy 复刻，**sklearn 移出运行时** |
| selenium 绑在核心依赖里 | 容器为了不用的爬虫装一整套 Chrome | 拆到 `[crawler]` optional extra |
| 前端与后端耦合在同一个包内 | 界面换不动、也无法单独交付给别人 | 前端移到顶层 `frontend/`（纯静态、可独立部署），后端只给 `/api/*`；由 `WQ_SERVE_FRONTEND` / `WQ_FRONTEND_DIR` 控制是否顺带托管 |
| 本地开单文件 HTML、容器开模板页 | 两种用法界面不一致，改一处要改两处 | 统一为**同一套前端**：本地启动器与容器都访问 `http://127.0.0.1:<port>/` |

## 二、快速开始

```bash
# 构建
docker build -t water-quality:0.9.0 .

# 运行（推荐：数据与日志挂卷）
docker run -d --name wq -p 5000:5000 \
  -v wq-data:/app/data \
  -v wq-logs:/app/var/logs \
  -e WQ_TZ=Asia/Shanghai \
  water-quality:0.9.0

# 打开 http://127.0.0.1:5000/
```

纯演示（不挂卷，用镜像内自带的 CSV 快照，重启即回到初始状态）：

```bash
docker run --rm -p 5000:5000 water-quality:0.9.0
```

验证：

```bash
curl -s http://127.0.0.1:5000/api/data_status
curl -s http://127.0.0.1:5000/api/predict
docker inspect --format '{{.State.Health.Status}}' wq
```

`ST10 2.4268 / ST11 2.0986 / ST12 2.1003 / ST13 2.6596 / ST14 2.5435`

## 三、环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `WQ_ROOT` | 从源码树推导 | 项目根。容器里是 `/app`。**装进 `site-packages` 后必须显式设置** |
| `WQ_DATA_DIR` | `$WQ_ROOT/data` | 数据目录（建议挂卷） |
| `WQ_MODELS_DIR` | `$WQ_ROOT/models` | 权重目录 |
| `WQ_LOGS_DIR` | `$WQ_ROOT/var/logs` | 日志目录（建议挂卷） |
| `WQ_TRUST_PROXY` | `true` | 是否信任穿透/反向代理带来的 `X-Forwarded-*`（挂 `ProxyFix`）。**穿透部署必须开**，否则应用看不到用户真实的协议/主机/路径前缀 |
| `WQ_SERVE_FRONTEND` | `true` | 是否由后端顺带托管 `frontend/`。设 0 则只提供 API，前端另交静态托管 |
| `WQ_FRONTEND_DIR` | `$WQ_ROOT/frontend` | 前端目录位置（前端与后端分开部署时用） |
| `WQ_HOST` | `0.0.0.0` | 监听地址。桌面单机可设 `127.0.0.1` 避免暴露到局域网 |
| `WQ_PORT` | `5000` | 端口 |
| `WQ_TZ` | `Asia/Shanghai` | **业务时区**（定时任务、报告日期）。容器默认 UTC，不设会让定时任务差 8 小时。未设时跟随 `TZ` |
| `TZ` | `Asia/Shanghai`（镜像已设） | 进程与**日志**时区。与 `WQ_TZ` 设成同一个值，否则日志时间和业务时间会差 8 小时，排障时极易误读 |
| `WQ_ENABLE_SCHEDULER` | `true` | 多 worker 部署**必须设 `0`** |
| `WQ_CRON_HOUR` / `WQ_CRON_MINUTE` | `2` / `0` | 定时采集时刻（按 `WQ_TZ` 解释） |
| `WQ_MAX_INSTANCES` | `1` | 同一任务并发上限 |
| `WQ_MISFIRE_GRACE` | `3600` | 错过触发点的容忍秒数 |
| `WQ_DEBUG` | 关 | 调试模式，生产不要开 |
| `WQ_CORS_ORIGINS` | `*` | 跨源白名单（逗号分隔）。前端由后端托管时同源、用不上；只有把前端单独部署到别的来源时才需要收紧 |
| `WQ_CHROMEDRIVER` / `WQ_HEADLESS` / `WQ_CRAWLER_URL` / `WQ_CRAWL_DEADLINE` | 见 `config.py` | 采集相关，需装 `[crawler]` |

完整清单与默认值见 `src/water_quality/config.py`，或启动日志里的配置摘要。

## 四、多 worker 与调度器（最容易踩的坑）

调度器跑在**应用进程内**，而 `gunicorn -w N` 会让每个 worker 各 import 一次应用模块。

- **默认 `-w 1`**：调度器与 Web 同进程，简单且不会重复采集。本项目规模推荐这样。
- **要横向扩容**：把 Web 与定时任务拆开。

```bash
# Web 层：关掉调度器，可以开多个 worker
docker run -d --name wq-web -p 5000:5000 \
  -v wq-data:/app/data \
  -e WQ_ENABLE_SCHEDULER=0 \
  water-quality:0.9.0 \
  gunicorn --bind 0.0.0.0:5000 --workers 4 --threads 4 water_quality.app:app

# 调度层：单进程，只跑定时任务
docker run -d --name wq-cron \
  -v wq-data:/app/data \
  -e WQ_ENABLE_SCHEDULER=1 \
  water-quality:0.9.0 \
  python -m water_quality.app
```

SQLite 连接是「每次请求新建、用完即关」，不跨线程复用，因此多 worker / 多线程是安全的；
WAL 模式让读不阻塞写。但注意：**SQLite 不适合多容器同时写同一个库文件**，
上面这种「一个 Web + 一个调度、共享同一个卷」的用法是安全的，再多就要换 PostgreSQL 了。

## 五、模型文件的格式（安全相关）

镜像里的 `models/` 有两个文件，缺一不可：

| 文件 | 内容 |
|---|---|
| `sequential_river_tn_model.pth` | 只含 `model_state_dict`，**纯张量**，可用 `torch.load(weights_only=True)` 加载 |
| `sequential_river_tn_model.meta.json` | `model_config` + 14 个输入缩放器 + 5 个目标缩放器 + 训练指标 |

**为什么拆开**：旧格式把 sklearn 的 `StandardScaler` 对象 pickle 进了 `.pth`，
迫使加载端写 `weights_only=False`——那会执行 pickle 里的任意对象构造，
等价于「只要 `.pth` 被替换就能执行任意代码」。镜像里的模型往往来自挂载卷或镜像仓库，
这个攻击面必须关掉。

**旧格式的 `.pth` 仍然能加载**（会打告警），迁移方式：

```bash
python scripts/migrate_checkpoint.py          # 迁移 + 自动逐位校验 + 备份
python scripts/migrate_checkpoint.py --check  # 只看状态，不改文件
```

`ml/train.py` 重训时也会直接输出新格式，因此**不会**在下次训练后把漏洞带回来。

## 六、镜像体积

| 做法 | 效果 |
|---|---|
| torch 走 CPU-only 索引 | 默认 wheel 带整套 CUDA，镜像数 GB；CPU 版小一个量级。只用得上 CPU 前向推理 |
| sklearn 移出运行时 | 少一个较大的依赖；容器里不再需要它 |
| `.dockerignore` 排除 `.git`/日志/数据库/文档 | 构建上下文更小、更快 |
| 浏览器只装 `chromium-driver` | 该包本身把 chromium 作为硬依赖带入（光有驱动无法工作），不再额外声明浏览器与字体包 |

**当前实测体积：约 2.8 GB**（未装浏览器驱动时约 1.69 GB）。

其中 `chromium-driver` + 其依赖链约占 **+1.1 GB**。这笔体积是**采集能力**的代价：

- 数据源页面是 JS 渲染的（省份下拉 + iframe + 滚动加载），纯 `urllib` 拿不到表格；
- 没有驱动时，一旦站点恢复，定时任务会在 `_make_driver()` 处抛
  `ModuleNotFoundError: No module named 'selenium'` —— 而且因为站点当前不可达，
  这个问题会被"预检失败"挡住，平时看不出来；
- 不想要自动采集时，设 `WQ_ENABLE_SCHEDULER=0` 关掉调度即可（依赖仍在镜像里）。

**不需要单独安装 CJK 字体包**：爬虫按 DOM 文本定位（`//a[text()='湖南省']`），
不依赖字形渲染；实测容器内能正确取回中文断面名并解析出记录。

若 CPU 索引暂时没有钉住的 torch 版本，Dockerfile 会回退到 PyPI（镜像更大但能构建成功）。

## 七、排障

**启动日志里先看这几行**（应用启动时会打印）：

```
项目根=/app 时区=Asia/Shanghai 调度器=on
调度器已启动：每日 02:00（Asia/Shanghai）执行 run_daily_pipeline
```

若看到 `检测到包已安装到 site-packages，但未设置 WQ_ROOT` —— 说明路径推导不可靠，
显式设置 `WQ_ROOT` 指向项目根。

| 现象 | 原因 | 处理 |
|---|---|---|
| 容器起来但访问不了 | 监听了 `127.0.0.1` 而不是 `0.0.0.0` | 设 `WQ_HOST=0.0.0.0` |
| 定时任务在错误的时间跑 | 容器是 UTC | 设 `WQ_TZ=Asia/Shanghai` |
| `database is locked` | 多进程写同一个 SQLite | 见第四节；单容器多线程是安全的 |
| 日志目录报权限错误 | 挂载卷属主不是 uid 10001 | `chown -R 10001` 或改用命名卷 |
| 预测报「No input data」 | `data/processed/` 为空 | 挂载数据卷，或用 `pipeline.ingest` 导入数据 |
| 重复采集 | 多 worker 都启动了调度器 | 设 `WQ_ENABLE_SCHEDULER=0` |

## 九、容器里不能用 `.bat`（以及已经做的处理）

`启动平台.bat` 是 Windows 批处理，在 Linux 容器里**根本执行不了**：

| `.bat` 里的内容 | 在容器里的问题 |
|---|---|
| `chcp 65001` | `chcp` 是 Windows 命令，Linux 里不存在 |
| `cd /d "%~dp0"` | `%~dp0` 与 `cd /d` 都是 cmd.exe 语法，`sh` 里无意义 |
| `set "PYTHONPATH=%~dp0src"` | 反斜杠路径分隔符在 Linux 下无效 |
| `pause` | 等待按键；容器无 stdin/TTY 时会**挂住不退**，一直占着进程 |

就算绕过这些直接跑 `python -m water_quality.launcher`，原来还有两个坑：

1. `webbrowser.open()` 会去找图形浏览器 —— 容器里没有，只会**白等 30 秒**再失败；
2. 它打印 `http://127.0.0.1:5000/`，而容器里的 `127.0.0.1` 指容器自己，
   你在宿主机浏览器里**打不开**。

已经做的处理：

- `launcher.py` 增加 `in_container()` 与 `browser_available()`，
  **自动识别无图形环境并跳过打开浏览器**（不再白等 30 秒）；
- `service_url()` 在容器里明确提示需要 `-p 端口:端口` 映射，而不是给出误导性的 `127.0.0.1`；
- 新增 `启动平台.sh` —— Linux / macOS / 容器内的等价入口，
  用 `exec` 启动以便正确转发 `Ctrl+C` 与 `docker stop` 的信号，并保证 LF 换行
  （`.gitattributes` 里 `*.sh text eol=lf`，CRLF 会导致 `bad interpreter`）；
- 容器镜像的入口是 Dockerfile 的 `CMD`（gunicorn），不依赖任何脚本。

容器里正确的启动方式：

```bash
docker run -d -p 5000:5000 water-quality:0.9.0                                      # 镜像默认 CMD
docker run --rm -p 5000:5000 water-quality:0.9.0 python -m water_quality.launcher   # 调试用启动器
```

`.bat` 仍保留在仓库里供 Windows 使用；它没有被打进镜像（见 `.dockerignore`）。

## 十、远程访问与内网穿透（当前主要部署形态）

本项目**不需要离线单文件版** —— 部署形态就是「Docker 跑后端 + 内网穿透 + 远程打开」。
单文件导出脚本与前端的内置快照回退分支都已移除。

### 做法

```bash
docker compose up -d --build          # 仓库里已备好 docker-compose.yml
```

然后把穿透服务（frp / ngrok / cpolar / 花生壳 …）指向**宿主机的 5000 端口**即可。
`compose` 里已经设好了穿透场景需要的几项：

| 环境变量 | 值 | 为什么 |
|---|---|---|
| `WQ_HOST` | `0.0.0.0` | 监听回环则穿透转发不进来 |
| `WQ_TRUST_PROXY` | `1` | 信任 `X-Forwarded-*`，否则应用以为自己在 `http://内网IP:5000` |
| `WQ_SERVE_FRONTEND` | `1` | 由后端一并托管前端，单容器最省事 |
| `TZ` / `WQ_TZ` | `Asia/Shanghai` | 日志时间戳与业务时间保持一致 |

### 两种穿透形式都能用

**① 子域名 / 端口形式**：`https://wq.example.com` → 宿主机 `5000`
最常见，直接可用。

**② 子路径形式**：`https://主站/wq/` → 容器 `/`
也**不需要改任何配置**。前端所有资源与接口都走相对路径：

```
页面在  https://主站/wq/
资源    https://主站/wq/assets/css/app.css   ← 相对路径自动带上 /wq/
接口    https://主站/wq/api/data_status      ← 同上
```

这一点必须强调：早期版本把接口写成 `/api/...`（域名绝对路径），子路径穿透下会被解析成
`https://主站/api/...`，全部 404。已改为相对路径并实测通过。

实测（本地反向代理模拟子路径穿透）：

```
页面地址      http://127.0.0.1:5092/wq/
状态栏        就绪
实际调用的接口  http://127.0.0.1:5092/wq/api/data_status
属性表 1200 行 / 地图 14 个标记 / 控制台 0 报错
```

### 远程访问要留意的两件事

1. **地图底图由浏览器直连高德**。客户端能上外网就正常；纯内网客户端只能看到
   纯色底图与断面标记（界面与数据不受影响）。若要完全离线底图，需自行准备瓦片服务。
2. **HTTP 还是 HTTPS**：穿透若提供 HTTPS，页面与接口同源，不存在混合内容问题。
   只有把前端单独部署到别的来源时，才需要 `apiBase` + `WQ_CORS_ORIGINS`。

### 排障

| 现象 | 原因 | 处理 |
|---|---|---|
| 穿透地址打开是 502 / 无法连接 | 容器只监听了回环 | `WQ_HOST=0.0.0.0` |
| 页面能开但数据一直空、状态栏红色 | 子路径穿透下接口 404（老版本问题） | 已是相对路径；确认没被中间的 nginx 重写掉 `X-Forwarded-Prefix` |
| 日志里 URL 是内网 IP | 没信任代理头 | `WQ_TRUST_PROXY=1` |
| 地图一片灰但有断面点 | 客户端连不上高德瓦片 | 正常降级；或改 `app.config.js` 的 `basemaps` 指到自有瓦片 |
