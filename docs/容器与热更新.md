# 容器与热更新

> 原则：**镜像只是产物，开发期一律走热更新**。改代码 → 刷新，不要为了看一个改动去重建镜像。
> 镜像定型（交付/上云）时才把产物"烤"进去。

## 一、三处热更新点

| 改什么 | 怎么生效 | 要多久 |
|---|---|---|
| 后端 `src/` | 已用 `./src:/app/src:ro` 挂进容器 → `docker restart wq` | 几秒 |
| 主应用（file:// 形态） | `python scripts/build_frontend.py --api-base https://localhost:8443` → 浏览器刷新 | 1-2 秒 |
| 前端容器（同源形态） | `python scripts/build_frontend.py --out build/dist-docker` → 浏览器刷新（目录已挂进容器） | 1-2 秒 |
| `deploy/nginx.conf` | `docker exec wq_fe nginx -s reload` | 1 秒 |
| `deploy/Caddyfile` | `docker exec wq_web caddy reload --config /etc/caddy/Caddyfile` | 1 秒 |

**前端为什么不用重启容器**：nginx 只是把 `/usr/share/nginx/html` 当目录读，
宿主构建目录挂进去以后，文件一变页面就变（配合 `index.html` 的 `no-store`）。

## 二、两种前端形态，产物不一样（容易踩）

| 形态 | 构建命令 | `apiBase` | 页面地址 |
|---|---|---|---|
| 双击打开（file://） | `build_frontend.py --api-base https://localhost:8443` | 绝对地址 | `dist/index.html` |
| 容器同源（nginx） | `build_frontend.py --out build/dist-docker` | **空串** | `http://主机:8088/` |

两者输出到不同目录，互不覆盖。**别把带 `apiBase` 的产物拿去做容器**——
那样页面会绕过 nginx 直连 8443，同源的意义就没了。

## 三、开发期直接起"一前一后"两个容器（推荐）

仓库里已经有一份现成的热挂载编排：`deploy/docker-compose.hot.yml`

```powershell
# 1) 构建同源产物（前端容器用的那份）
python scripts/build_frontend.py --out build/dist-docker

# 2) 起两个容器
docker compose -f deploy/docker-compose.hot.yml up -d

# 3) 打开 http://127.0.0.1:8080/
```

它做的事：

| 容器 | 镜像 | 热挂载 | 端口 |
|---|---|---|---|
| `wq_hot` | `water-quality:0.9.2` | `./src → /app/src`（只读） | 内网 5000 |
| `wq_hot_fe` | `water-quality-frontend:0.9.2` | `./build/dist-docker → /usr/share/nginx/html` | 8080→80 |

与现有 `wq` / `wq_web`（8443）**互不影响**：独立容器名、独立数据卷、独立网络。
开发期后端命令带 `--reload`，`src/` 里文件一变 worker 自动重启（约 1 秒），
连 `docker restart` 都不用。

**实测（2026-10-21）**

- 往 `build/dist-docker/` 放一个 `hot-probe.txt`，`curl http://127.0.0.1:8080/hot-probe.txt`
  立刻返回该内容 → 前端产物是活挂载，不用重建镜像；
- `touch src/water_quality/app.py` 后，日志里 `Booting worker` 次数 +1，
  `/api/data_status` 仍是 200 → 后端代码热生效；
- `docker exec wq_hot python -c "import water_quality.app as m; print(m.__file__)"`
  → `/app/src/water_quality/app.py`（确认加载的是挂载进来的代码）。

> 顺带一个 nginx 行为要记住：`location /` 用了 `try_files … /index.html`，
> 所以**任意不存在的路径都会回退成首页并返回 200**；只有 `/assets/` 下是 404。
> 判"产物有没有更新"要看内容，不能只看状态码。


## 四、打镜像（定型时才做）

```powershell
# 前端：先用同源产物构建，再打包
python scripts/build_frontend.py --out build/dist-docker
docker build -f Dockerfile.frontend -t water-quality-frontend:0.9.2 .

# 后端：源码/模型/数据烤进镜像（src 的挂载只影响开发期）
docker build -t water-quality:0.9.2 .
```

**后端全量构建很慢**（torch CPU + chromium-driver 两层，网络不好要十几分钟）。
只改了 `src/` 而依赖没变时，用增量构建：

```powershell
docker build -f build/Dockerfile.backend-hot -t water-quality:0.9.2 .
```

它 `FROM smartwaterqualityearlywarningplatform:0.9.1`（已装好全部依赖）
再 `COPY src/`，5 秒左右出新镜像。**定型交付时仍要用根目录的 Dockerfile 全量构建**，
保证镜像可复现；增量镜像只用于开发期。

两个镜像互相独立：后端只有 `/api/*`，前端只有静态文件 + 反代。
换前端不用动后端，换后端不用动前端。

## 五、生产形态与开发形态的差别

| | 开发 | 生产 |
|---|---|---|
| 前端 html | 宿主目录挂进容器 | 烤进镜像（删掉 `-v` 那行） |
| 后端 `src/` | 挂载 + restart | 烤进镜像（compose 里注释掉 `./src:/app/src:ro`） |
| 镜像 tag | 可以随手覆盖 | 一个版本一个 tag，不回填 |

上线前把上表的"挂载"去掉，`docker compose up -d` 就是一份可复现的部署。
**在那之前不要把挂载删掉**——删了就得每次改代码都重建镜像。
